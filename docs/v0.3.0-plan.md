# V0.3.0 计划：L2 文件级快照

> 日期：2026-10-17。前置研究：[docs/m6-research.md](m6-research.md)（结论 GO）。
> 目标：kernel 承载的环境以**整个浏览器 profile**为快照单位，IndexedDB / Service Worker / 密码库等
> 全部站点数据随基线漫游；builtin 承载保持 L1 结构化数据面不变。

## 1. 设计

### 1.1 数据模型（客户端，服务端零改动）

- **快照 kind**：manifest `kind: 'files'`（v0.1.0 schema 已预留）；`payload.format: 'tar+gzip'`，
  附 `kernelVersion`（内核构建标识）与 `seed`（指纹种子）。
- **blob 格式（L2 专用）**：raw 二进制密文 `[12B nonce][AES-256-GCM 密文][16B tag]`，
  与 L1 的 base64(JSON 信封) 并存（L2 体积大，避免 base64+JSON 双重膨胀）。
- **子密钥派生**：与 L1 同构，HKDF purpose `snapshot-files:<snapshotId>`。
- **打包**：tar.gz（V0.3 用 gzip 零依赖；zstd 列为后续优化），排除缓存类目录
  （`Cache`、`Code Cache`、`GPUCache`、`GPUPersistentCache`、`GraphiteDawnCache`、`GrShaderCache`、
  `ShaderCache`、`Crashpad`、`tmp` 等）——它们体积大且可再生。

### 1.2 容器 profile 直通（Docker 内核）

- `DockerKernelLauncher` 改为 `-v <userDataDir>:<userDataDir>` 挂载宿主目录——容器内
  --user-data-dir 指向同一物理目录，profile 落在宿主机，容器删除不丢数据。
- **抓取**：`docker pause`（冻结全部进程，等效一致性快照）→ 宿主侧 tar → `docker unpause`。
  环境保持运行，用户无感。
- **恢复**：解密解包到 per-run 宿主目录 → 正常 `docker run` 挂载该目录 → 内核启动即见全部数据，
  **零数据面注入**。
- 原生内核（mac/win）L2 抓取暂不支持（当前 mac 预编译产物不可用于 Intel 开发机；
  且原生 os_crypt 绑定系统钥匙串，需 V0.4+ 补丁路线），报错明确提示。

### 1.3 管线接入（AppService）

- `uploadSnapshot`：`hosting === 'kernel'` → L2 路径（pause→tar→sealFiles→上传）；
  builtin → L1 结构化（不变）。
- 恢复（openEnv / 互斥接管）：先取 manifest 判 kind——`structured` → 现有 restore 注入；
  `files` → 解密解包为 restoreDir 传给 `host.open`。L2 快照恢复到 builtin 环境 → 明确报错
  （跨承载迁移需经运行中的 kernel 环境抓 L1）。
- **内核版本绑定**：manifest.kernelVersion ≠ 当前内核 → 允许打开但 warning 提示
  「内核版本变化，如登录态异常请重新登录并更新基线」。
- 模式二驱逐上传：kernel 环境自动走 L2（gzip 压缩级别 1 以赶 15s 驱逐期限，e2e T3k 验证）。

### 1.4 UI

环境卡片基线徽标区分「文件级（kernel）」/「结构化（builtin）」；保存基线按钮文案不变。

## 2. 验收矩阵

| # | 场景 | 断言 | 载体 | 状态 |
|---|---|---|---|---|
| T-L2.1 | kernel 环境：登录 + IndexedDB/localStorage/持久 cookie → 保存基线 → 关闭 → 新实例克隆 | 三类数据全部读回（cookie 经叠加 L1 注入补会话 cookie；LS/IDB 经 profile） | e2e-l2（docker） | ✅ |
| T-L2.2 | L2 基线 manifest | kind=files + tar+gzip + 内核版本/种子绑定 | e2e-l2 | ✅ |
| T-L2.3 | 模式二 kernel 驱逐上传（L2 双写）在驱逐期限内完成 | T3k 语义不变（驱逐→接管→免登录） | e2e-interop 回归 | ✅（13/13） |
| T-L2.4 | L2 基线 → builtin 环境 | 双写 L1 副本自动回退（比计划中的「报错」更强的语义） | e2e-l2 | ✅ |
| 回归 | L1 全链路 | builtin 17/17 · interop 13/13 · fp 10/10 · kernel-smoke 7/7 | 全套 | ✅ |

> 实现与计划的偏差：计划中 builtin 打开 L2 基线「明确报错」，实现升级为**双写 + L1 回退**（kernel 保存时同步上传结构化副本，其 id 存环境配置），双承载互迁移承诺不回退；驱逐上传因此变为双份，经 T3k 实测仍在期限内。

## 3. 里程碑

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| S1 引擎与启动器 | sealFiles/openFiles（二进制信封）+ tar 打包/解包（缓存排除）+ Docker 挂载直通与 pause 抓取 | 单元级冒烟：抓取→密封→打开→解包 round-trip |
| S2 管线接入 | uploadSnapshot L2 分支 + openEnv/接管恢复分支 + 版本绑定提示 + UI 徽标 | 手动跑通 T-L2.1 |
| S3 验收 | e2e-l2 + 全量回归 + 发版 tag v0.3.0 | 验收矩阵全绿 |

## 4. 风险与对策

- **挂载性能**（Docker Desktop virtiofs）：Chromium I/O 经挂载可能变慢 → e2e 观察启动/页面耗时；
  若不可接受回退 `docker create → cp → start` 预置方案。
- **驱逐期限**：15s 内完成 tar+gzip+加密+上传 → gzip level 1 + 缓存排除控制体积；e2e 实测。
- **体积增长**：首版全量快照（预计 20–80MB/环境）→ 保留策略已有（N=5）；增量快照列 V0.4。
- **virtiofs 下的 SQLite/LevelDB 一致性**：pause 冻结后宿主侧读取，规避并发写。
