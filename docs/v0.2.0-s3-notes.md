# V0.2.0-S3 排障记录与已知问题

> 日期：2026-10-10。S3（指纹与代理）开发过程中的关键发现、修复与遗留问题。

## 已修复（本轮排障的实战收获）

1. **`docker run` 必须等待命令完成**（execFileP），`spawn` 的 `spawn` 事件仅代表进程创建——不等完成会导致后续 `docker wait` 报 `No such container`，并引发一系列时序性假挂死。
2. **页面级 CDP WebSocket 在导航引发渲染进程切换后失效**（evaluate 永久无响应）——产品路径全部改为 browser-level 连接 + `Target.attachToTarget(flatten)` 的 `PageSession`（Puppeteer 同款做法）。
3. **CDP 命令必须带超时**（CdpConnection 默认 20s），否则一个无响应页面可挂死整个应用；poll 类工具要同时捕获 rejection 与挂起。
4. **headful Chromium 忽略 `--remote-debugging-address`**：容器内 CDP 只绑 127.0.0.1，用 socat 转发到 0.0.0.0（scripts/kernel-docker/entrypoint.sh）。
5. **Chrome 150 移除自动 SwiftShader 回退**：容器内 WebGL 需 `--use-angle=swiftshader-webgl --enable-unsafe-swiftshader`，否则 WebGL 上下文创建阻塞渲染器。
6. **`setProxy(<-loopback)` 会污染 Electron 网络服务的后续请求**：geoLookup 改用 Node 原生 socket 实现 HTTP 代理查询，不经 Chromium 网络栈。
7. **localStorage 经临时 tab 注入后需等待落盘（~400ms）再关 tab**，且对已加载页面需 Page.reload 才能读到注入值。
8. **kernel-smoke 与 cdp.ts 重构的 API 适配遗漏**（`'Page.enable' wasn't found`）：browser 级连接上没有 Page 域，必须经 session 发送——重构公共模块时所有调用方要同步适配并有回归兜底。

## 已知问题（遗留）

### KI-1：AppService 路径下的 kernel 指纹读取挂死（e2e-fp）——✅ 已解决（V0.2.0-S4）

- **现象**：`--e2e-fp` 中经 `AppService.openEnv → ExternalKernelHost.open` 启动的容器，`Runtime.evaluate`（含 canvas/WebGL 的表达式）无响应（20s 超时）；同一容器内新建 about:blank 标签正常；外部独立进程探测同样无响应（页面 renderer 阻塞在 futex）。
- **已排除**（逐一单变量验证均正常）：seed 值、platform 值、时区/语言 flags、代理有无、参数顺序、含空格/深层 user-data-dir、Network.enable、attach 时机（含 4s/9s 稳定等待）、docker wait 子进程、detached 发起、bind-ip、镜像 flags 组合、Electron 发起（裸脚本同参数全绿）。
- **对照**：`--kernel-smoke --docker`（不经 AppService）在同一 Electron 进程内同参数全绿（7/7，含 T10 同 seed 跨设备一致性）。
- **根因（S4 定位，apps/desktop/scripts/probe-kernel.mjs 裸 Node 二分法）**：
  1. **S3 的「seed 值已排除」结论有误**——裸 Node + docker 用挂死现场的完整参数即可复现，与 Electron/AppService 前置状态完全无关；
  2. 二分命中 seed 本身：`--fingerprint` 官方要求 **32-bit 整数**，而现场 seed `aaaa-seed-t9`（及一切非数字串如 `abc`）解析失败；
  3. 进一步定位：死锁点不是 canvas/WebGL，而是**首次读取 `navigator.hardwareConcurrency`**（内核对该属性的伪装计算在非法 seed 下退化为永久 futex 等待）；`1+1`、`navigator.userAgent`、canvas-only 均正常，hc 读取后整个浏览器级联挂死（新标签 Page.enable 也无响应）；
  4. 数字 seed（含 0）全部正常。kernel-smoke 一直没踩中是因为它的 seed 恰好都是数字；产品代码 `createEnv`/`refreshEnvs` 的 `seed || randomId()` 回退（UUID hex 串）则**必然**踩中——真实网站上风控脚本普遍读 hc，属产品级缺陷（未发布，无外溢）。
- **修复（S4）**：`randomSeed()`（1~2147483647 随机整数）+ `isValidSeed()` 校验（createEnv 拒绝非法输入）；`refreshEnvs` 对缺失/非法 seed 回填合法值并**回写云端**（保证指纹跨设备稳定不漂移）；e2e seed 全部改数字。修复后 e2e-fp 10/10 全绿（含新 T13）。
- **经验**：单变量排查的结论要对「变量取值集合」敏感——当时只试了数字 seed 之间的差异，没试「数字 vs 非数字」这一维；上游内核的输入约束（README 明写 32-bit integer）应作为第一道假设。

### KI-2：容器内核上 Intl/locale 类 JS 读取不稳定——✅ 已解决（与 KI-1 同源）

页面侧 `Intl.DateTimeFormat().resolvedOptions()` 等读取在容器内核上偶发挂死（与 KI-1 可能同源）。
**根因同 KI-1**：非法 seed。合法 seed 下 Intl 读取恢复稳定（S4 实测 `--timezone=Asia/Shanghai --lang=zh-CN` 下返回 `Asia/Shanghai / zh-CN`，多次读取稳定）。FP_EXPR 已恢复全部字段（tz/lang/mem），T13 改为页面侧 Intl 断言。

## S4 补充修复（同轮）

- **/v1/geo 私网分支时区错报 UTC**：`time.Local.String()` 在 macOS/Linux 常返回 `"Local"`（Go 无法从 /etc/localtime 内容反推 IANA 名）→ 被 `tz == "Local"` 兜底成 UTC。改为按 TZ 环境变量 → /etc/localtime 符号链接（`…/zoneinfo/<名字>`）→ time.Local 的顺序解析（server/internal/geo/geo.go `localTimezone()`）。
- **test-site 代理补 X-Forwarded-For**、/fp 页改渲染 `clientIP(r)`（经代理回显真实来源）——支撑 T13.3 断言。
- **T13 断言的可达性**：Docker Desktop 下容器→宿主机流量经 host 栈 NAT，代理侧来源恒为宿主机 IP，「来源=容器 IP」不可断言；改用「代理日志含页面请求 + 站点来源非 docker VM 直连网段（192.168.65.x）」。
