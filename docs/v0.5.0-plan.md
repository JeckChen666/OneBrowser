## 1. 自动更新（electron-updater 两阶段）

**背景**：安装包已稳定产出（nsis x64 + blockmap，120MB），但更新靠手动重装。
blockmap（差分更新的原料）electron-builder 已在产出，尚未启用。

**关键依赖：代码签名**。未签名安装包在 Windows 上无法静默更新（SmartScreen/UAC 拦截），
且 electron-updater 差分下载的信任链也建议建立在签名之上。证书未到位前只做阶段 a。

- **阶段 a（无签名可做，估时 2 天）**：
  - `electron-builder.yml` 补 `publish: github`，dist 产物随 tag 推上 GitHub Releases；
  - 渲染层「关于/检查更新」入口：主进程 `GET Releases/latest` API 比对版本号，
    有新版 → 通知 + 一键打开 Releases 下载页（不自动安装）；
  - 启动后 24h 节流检查一次；版本号显示已在顶栏（V0.4.2 已接线）。
- **阶段 b（证书到位后，估时 3 天）**：
  - electron-updater 全量接入：后台下载（差分 blockmap）→ 就绪提示 → 重启安装；
  - mac dmg 同步接入（`identity` 换真实证书，现为 ad-hoc null）；
  - 壳与内核分离更新不变：内核已有独立下载渠道（kernelManager）。

**出口标准**：
- a：App 内点「检查更新」能正确报告「有新版 vX.Y.Z / 已是最新」；下载页直达对应 tag。
- b：旧版 App 内完成下载→安装→重启，版本号变化；二次验证差分体积 < 全量 30%。

## 2. 增量快照（先量化，后决定；默认不做）

**背景**：L2 快照 = 全量 tar+zstd，每快照独立密钥（`subkey(dek, snapshot-files:${snapId})`），
retention 5 自动清理。当前测试基线仅 36KB——全量毫无压力。痛点假设来自重度 profile
（IndexedDB / Service Worker / 浏览历史增长到几十~几百 MB 时，每次保存全量上传）。

**决策门（量化先行，估时 1 天）**：用真实重度 profile 构造 3 档样本（10MB / 50MB / 200MB），
实测「二次保存」耗时与体积。**若 50MB 档保存 < 5s（本机 SSD+普通上行），V0.5 不做**；
超标才立项。立项方案（客户端编排，服务端零改动）：

- 清单级 diff：恢复端保留最近基线的解包目录与逐文件 hash 清单；保存时比对
  （path/size/mtime 预筛 + hash 确认），仅对变更/新增文件追加 tar 分片上传；
- 恢复端：base 对象 + delta 分片按清单合成（密钥体系无需变——per-snapshot 派生
  本就覆盖新分片）；
- retention 交互：基线被 GC 时 delta 链失效，需 rebase（删链上独立快照或就地快照化）。

**出口标准（若立项）**：二次保存体积 < 全量 15%；恢复后与全量恢复逐字节等价
（cookie/localStorage/IndexedDB 三面断言）；retention 清理不破坏可恢复性。

## 3. 团队协作（V0.5 交付设计定稿，实现切 V0.6）

**背景**：现状是单账号多设备（同一 wrapped DEK，各自密码 KEK 解封）。用户间共享只能共享
账号密码——密钥 hygiene 差（离职=改密码+重包裹，且无审计粒度）。

**设计核心（增量演进，不动现有单人路径）**：

1. **用户身份密钥对**：每用户新增 X25519 静态密钥对；私钥由本人 KEK 包裹上云
   （与 wrapped_dek 同构），公钥明文列（服务端可见，用于他人包裹）。
2. **团队 = 独立 DEK + 成员信封**：`teams` 表 + `team_members` 行携带
   `wrapped_team_dek`（用成员公钥包裹）。团队环境的 configEnc 与快照全部改由
   team DEK 派生（`subkey` purpose 加 `team:` 前缀区分）。
3. **邀请流**：邀请人从服务端取被邀人公钥 → 包裹 team DEK → 写入其 membership 行；
   被邀人登录后解封即得。吊销 = 轮换 team DEK 并为剩余成员重包裹；
   被吊销者保留已缓存数据（UI 明示语义），无法获取新基线。
4. **服务端改动面**：两张表 + 邀请/吊销/列表三个端点（均在登录中间件内），
   全程只见密文与公钥；运维工作台加团队只读视图。
5. **互斥租约语义**：团队环境的 lease 天然支持跨成员互斥（lease 按设备 ID，与账号无关），
   驱逐通知需带成员身份——ws 消息加 `holderEmail`（服务端明文可查）。

**V0.5 交付物**：本节设计评审定稿 + DB 迁移草案 + 邀请/吊销时序图 —— 见**附录 A**（已定稿）。
**V0.6 实现出口标准**：A 邀请 B → B 免登录打开团队环境基线；A 吊销 B 后 B 取不到新基线；
被驱逐通知显示操作成员邮箱；全程服务端零明文（S3 抽查密文断言）。

## 附录 A：团队协作 E2E 设计定稿（V0.6 实现蓝本，2026-10-28 评审定稿）

### A.1 密钥对象与存储

| 对象 | 生成时机 | 私密份存储 | 说明 |
|---|---|---|---|
| 身份密钥对 X25519 | 注册时一次性生成 | 私钥由本人 KEK 包裹上云（`users.wrapped_identity_priv`） | 公钥明文列 `users.identity_pub`，任何登录用户可查（用于他人包裹） |
| team DEK（32B） | 创建团队时客户端生成 | 每成员一份：用其 `identity_pub` 包裹存 membership 行（`wrapped_team_dek`） | 服务端全程只见公钥与密文 |

包裹原语（`e2e.ts` 新增）：`wrapFor(recipientPub, key)` / `unwrapWith(myPriv, wrapped)`
= X25519-ECDH → HKDF-SHA256 → AES-256-GCM（需新增依赖 `@noble/curves`；`@noble/hashes` 已有）。

### A.2 DB 迁移草案（`0002_teams.sql`）

```sql
ALTER TABLE users ADD COLUMN identity_pub          TEXT NOT NULL DEFAULT '';
ALTER TABLE users ADD COLUMN wrapped_identity_priv TEXT NOT NULL DEFAULT '';

CREATE TABLE IF NOT EXISTS teams (
    id         TEXT PRIMARY KEY,
    name       TEXT NOT NULL,
    owner_id   TEXT NOT NULL REFERENCES users(id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS team_members (
    team_id          TEXT NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
    user_id          TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role             TEXT NOT NULL CHECK (role IN ('owner','admin','member')),
    state            TEXT NOT NULL DEFAULT 'active' CHECK (state IN ('pending','active')),
    wrapped_team_dek TEXT NOT NULL,   -- 用该成员 identity_pub 包裹的 team DEK
    joined_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (team_id, user_id)
);

-- 环境归属：NULL=个人环境（现状路径零迁移成本）
ALTER TABLE environments ADD COLUMN team_id TEXT REFERENCES teams(id) ON DELETE CASCADE;
CREATE INDEX IF NOT EXISTS idx_envs_team ON environments(team_id) WHERE deleted_at IS NULL;

-- 一次性邀请令牌（A 包裹好 DEK 直接写 pending membership；本表仅 email 通知场景预留）
CREATE TABLE IF NOT EXISTS team_invites (
    token      TEXT PRIMARY KEY,
    team_id    TEXT NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
    inviter_id TEXT NOT NULL,
    expires_at TIMESTAMPTZ NOT NULL
);
```

个人路径零改动：`team_id IS NULL` 的环境与现行完全一致。

### A.3 密钥派生与用途（换根不换管线）

团队环境的 configEnc / 快照 / os-crypt 密钥全部改以 team DEK 为根，**派生式原样复用**：

- `sealConfig(teamDek, envId, cfg)`（同构，只是根从个人 DEK 换 team DEK）
- `subkey(teamDek, 'snapshot-files:{snapId}')` / `subkey(teamDek, 'os-crypt:{envId}')`

因此 snapshotEngine / profileArchive / 内核 os-crypt 管线**零改动**；唯一接入点：
`appService.resolveRootKey(env)` —— personal → 解封的 DEK，team → 解封的 team DEK（按
membership 缓存）。

### A.4 邀请流时序（push 模型：邀请即包裹，接受才激活）

```
邀请人 A（owner/admin）          服务端                        被邀人 B
  | GET /v1/users?email=b@x       |
  |<-- {userId, identity_pub}     |   （公钥公开；未注册则 404）
  | wrapFor(B.pub, teamDek)       |
  | POST /v1/teams/{t}/members    |
  |   {userId, wrappedTeamDek, role} 
  |                               |--> 写 team_members(state=pending)
  |                               |--> ws: team.updated（B 侧提示有待接受邀请）
  |                               |<-- POST /v1/invites/{teamId}/accept --
  |                               |--> pending→active；ws: team.updated
  |                               |<-- B unwrapWith(identity_priv, wrapped_team_dek)
  |                               |    （此后 GET /v1/envs 可见团队环境，
  |                               |      configEnc 用 team DEK 解封）
```

拒绝 = decline → 删 pending 行（B 从未解封，DEK 副本无害但随行删除）。

### A.5 吊销流时序（软吊销默认，DEK 轮换为可选加固）

```
A（owner/admin）                服务端                       被吊销者 C 的设备
  | POST /v1/teams/{t}/members/{C}/revoke
  |                              |--> 删 team_members 的 C 行
  |                              |--> ws: team.updated（全员）
  |                              |<-- C 心跳发现无成员资格 → 本地关闭团队环境窗口、
  |                              |    清 team DEK 缓存、刷新环境列表
  ── 至此 C 的服务端访问已断（列表/上传/下载/presign 全 403）──
  可选加固：DEK 轮换（针对 presign TTL≤60min 窗口与 blob 直链泄露）
  | newTeamDek = generateDEK()
  | 对每个剩余成员 m：wrapFor(m.pub, newTeamDek)
  | PUT /v1/teams/{t}/dek（批量替换 wrapped_team_dek）
  | 团队环境配置：owner 轮换时旧根在手 → 全部重密封到新根（e2e TM.5 实测修正：
  |   否则刷新时配置解密降级，homepage/hosting 归零）
  | 旧快照：保持冷启动语义（旧根加密无法追封）——成员重登录+存新基线即恢复
```

**语义边界（UI 必须明示）**：C 在成员期内合法获取过的数据（已缓存的 profile/快照解密结果）
带得走——这是任何 E2E 分享系统的固有性质。硬吊销（历史快照全部重加密）成本高，**不提供**，
写入用户文档。

### A.6 服务端端点草案（均在登录中间件内；服务端零新增解密能力）

| 端点 | 说明 |
|---|---|
| `POST /v1/teams` {name} | 创建；创建者 owner；客户端本地生成 teamDek+自包裹 |
| `GET /v1/teams` | 我的团队（membership JOIN，含我的 wrapped_team_dek 与 role/state） |
| `GET /v1/users?email=` | 查公钥（仅返回 userId + identity_pub） |
| `POST /v1/teams/{t}/members` {userId, wrappedTeamDek, role} | 邀请（owner/admin；写 pending） |
| `GET /v1/teams/{t}/members` | 成员列表（email/role/state/joinedAt 明文元数据） |
| `POST /v1/teams/{t}/members/{u}/revoke` | 吊销（owner/admin，不可吊 owner） |
| `POST /v1/invites/{teamId}/accept\|decline` | 被邀人处理 |
| `PUT /v1/teams/{t}/dek` | DEK 轮换（owner；批量替换成员副本，服务端不解密） |
| `GET /v1/envs`（扩展） | `WHERE user_id=me OR (team_id IN 我的 active 团队)`，行带 teamId |

ws 消息新增 `team.updated`；互斥驱逐通知附 `holderEmail`（服务端明文可查，仅团队环境）。
运维工作台加团队只读视图（复用现有 admin 包模式）。

### A.8 安全性质与开放问题决议

**性质**：服务端全程只见公钥与密文；成员资格变更即时生效（authz 层）；吊销后新数据
不可读；与单人版 E2E 边界一致（admin 工作台同样只见元数据）。

**开放问题决议**：
1. 团队配额归属：**计入环境 owner**（个人=本人；团队=团队 owner 用户）——快照行加
   `owner_user_id` 归一化（实现时随迁移落地）。
2. 租约持有者展示：显示**成员 email**（团队环境）/ 设备号（个人环境）。
3. 硬吊销：**不提供**（§A.5 语义边界）。
4. 角色粒度：owner（全部+解散+转让）/ admin（邀请/吊销/改名）/ member（使用环境：
   打开/保存/编辑环境配置，不可邀请吊销）。
